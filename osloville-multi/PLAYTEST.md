# OSLOVILLE — real-time playtest protocol

Игра не становится «AAA» от одной красивой сборки: ей нужны повторяемые живые сессии, приоритизация проблем и короткий цикл исправления. Этот контур соединяет **профессиональных тестеров**, автоматический smoke-test и очередь багов, доступную агентам.

## 1. Поднять staging

```bash
cd osloville-multi
cp .env.local.example .env
# обязательно задайте длинный ADMIN_API_KEY и, для внешнего стенда, CORS_ORIGIN
# затем:
docker compose up --build
```

Откройте `http://localhost:3000` минимум в трёх независимых браузерных профилях/на трёх устройствах. Каждый тестер входит через **Play Demo** или Google (если настроен OAuth). Backend и WebSocket работают на `http://localhost:8080`.

> В production не используйте дефолтные PostgreSQL-пароли, не оставляйте `ADMIN_API_KEY` пустым и укажите точный HTTPS-origin в `CORS_ORIGIN`.

## 2. Сессия профессиональных тестеров (30–45 минут)

| Роль | Задача | Что считать проблемой |
|---|---|---|
| Explorer | Пройти 8 landmarks, A* маршруты, собрать предметы | застревание, телепорт, неверная награда, неясная цель |
| Social | 3 вкладки: чат, wave, одновременный сбор, reconnect | отсутствующий/дублированный игрок, потерянное сообщение, рассинхрон |
| Economy | Купить/надеть предметы, проверить недостаток монет | списание дважды, клиентская цена, неверная косметика |
| Mobile | Android/iOS: joystick, zoom, portrait, slow network | недоступные кнопки, gesture conflict, кадры/инпут с задержкой |
| Accessibility | Клавиатура, масштаб 200%, reduced motion, NVDA/VoiceOver | focus trap, нечитаемый текст, цвет как единственный сигнал |
| Soak | 20–30 минут в нескольких вкладках, reconnect | утечки, растущий lag, ghost-presence, ошибки после reconnect |

Для каждой критической ветки запишите **ожидание**, **факт**, шаги, устройство/браузер. Кнопка **🐞** в игре отправляет это в живую очередь. К ней автоматически добавляются FPS, координаты, район, погода, состояние сокета и browser signature — тестеру не нужно собирать их вручную.

### Severity

- **Blocker** — нельзя войти, ходить или продолжить playtest.
- **Major** — сломан core-loop (движение, награда, синхронизация, покупка).
- **Minor** — заметный UX/visual/accessibility дефект с workaround.
- **Idea** — гипотеза улучшения; не смешивается с багами.

## 3. Агентный QA gate перед каждой сессией

После запуска стека выполните:

```bash
cd osloville-multi/backend
PLAYTEST_URL=http://localhost:8080 npm run playtest:realtime
```

Скрипт поднимает три независимых Socket.io клиента и проверяет:

1. join/presence без offline «призраков» из БД;
2. разрешённое сервером пошаговое движение;
3. server-authoritative pickup и HUD update;
4. доставку чата и обновление speech-bubble всем игрокам;
5. server-authoritative покупку косметики;
6. reconnect той же учётной записи без ложного `player_left` и с восстановлением уже собранных pickup;
7. запись playtest report в очередь.

Он печатает JSON с `passed: true|false` и кодом возврата. Это smoke gate, а не замена людям: он ловит регрессии протокола до того, как тратить время тестеров.

## 4. Забор очереди и цикл исправления

Очередь защищена `X-Admin-Key` и намеренно не показывается обычным игрокам:

```bash
curl -H "X-Admin-Key: $ADMIN_API_KEY" \
  "http://localhost:8080/api/playtest-reports?limit=50"
```

Для каждого нового `blocker`/`major` агент делает один короткий цикл:

1. дедуплицирует report и формирует минимальные шаги воспроизведения;
2. воспроизводит баг через 3-пользовательский swarm и/или ручную сессию;
3. добавляет регрессионную проверку или расширяет `realtimePlaytest.ts`;
4. чинит минимальный слой (domain/use case, socket transport или UI);
5. запускает `npm run build` у `backend` и `frontend`, затем smoke test;
6. возвращает тестеру build id и просит подтвердить fix.

Не закрывайте bug только по локальной сборке: `fixed` означает «проверен первоначальным тестером на staging».

## 5. Важные ограничения стенда

- Сбор предметов и цена магазина валидируются сервером; браузер не является источником истины.
- Collectibles daily deterministic и доступны по `/api/world`; backend проверяет дистанцию до предмета.
- Очередь bug reports хранится в PostgreSQL в `playtest_reports` и переживает перезапуск приложения.
- Автоматический swarm создаёт один report уровня `idea` — фильтруйте его по заголовку `Automated real-time playtest heartbeat` при ручном triage.
